## Start from what you know

You have spent years managing networks built around servers that look roughly the same. A 1U or 2U chassis. Two CPUs. Some RAM. A handful of drives. One or two NICs running at 10GbE or 25GbE. The NIC is an afterthought -- a commodity part you order in bulk and never think about again.

The switch it connects to is familiar too. You understand spanning tree, ECMP, QoS queues. You can troubleshoot a flapping link without looking at the documentation.

This chapter is about how that familiar world collided with a fundamentally different problem -- and what the industry had to build from scratch to solve it.

---

## Act 1 -- The normal server

Before we go anywhere, let us establish the baseline. This is what normal enterprise infrastructure looks like:

<EnterpriseBaselineViz />

Nothing surprising. The CPU is the brain. The NIC moves data between the kernel and the wire. The network is there to connect services, not to compute.

The important characteristic of this world is not that the network can never be a bottleneck. Conventional workloads can be CPU-bound, memory-bound, storage-bound, or network-bound. Backup jobs, distributed storage, video pipelines, virtualization clusters, and database replication can all saturate modern links. The difference is one of degree and traffic shape: most enterprise application traffic is asynchronous, statistically multiplexed, and tolerant of small variations in delivery time.

A modern Ethernet NIC is also not an unintelligent frame pump. It uses DMA to move packets to and from host memory and commonly supports checksum offload, large-segmentation offload, receive-side scaling, interrupt moderation, flow steering, and virtualization offload. High-speed TCP/IP is achievable with appropriate hardware, software, and tuning. What changes in distributed AI is the combination of communication volume, tight synchronization, burst timing, congestion sensitivity, and latency requirements.

This is about to stop being true at AI-training scale.

**The host hardware path**

Before splitting work across servers, keep five resources distinct:

- **CPU and system RAM** run the operating system, application orchestration, data loaders, preprocessing, storage services, and communication setup.
- **GPU and HBM** execute compute kernels and provide very high-bandwidth accelerator memory. A kernel is a parallel program launched on the GPU.
- **PCIe** connects adapters and accelerators to the host. PCIe Gen5 x16 provides approximately 63 GB/s per direction before transaction-level overhead; this is not the same resource as GPU HBM bandwidth or external network bandwidth.
- **NIC DMA** allows a NIC to move data directly between the wire and registered memory without the CPU copying each byte. CPU software still configures queues, memory registrations, applications, and completion handling.
- **GPUDirect RDMA** is a supported path by which a compatible RDMA NIC can access GPU memory directly for eligible operations, avoiding an intermediate host-memory staging copy on the data path. Setup and orchestration still involve host software.

The simplified path is:

`CPU/RAM orchestration -> GPU kernel and HBM -> GPU interconnect or PCIe -> RDMA NIC -> external fabric`

<HostHardwarePathViz />

CPU involvement does not disappear merely because a GPU kernel or RDMA NIC is used. The correct mental model is division of labor, not absence of software.

## Act 2 -- What AI training actually requires

Training a large AI model is a different class of problem. To understand why, you need to understand what the computation actually looks like.

A neural network is a mathematical function with billions of parameters -- numbers that get tuned during training. The training process works like this:

1. Feed the model a batch of data
2. The model makes predictions
3. Measure how wrong the predictions are (the "loss")
4. Calculate how each parameter contributed to the error (gradients)
5. Nudge every parameter slightly in the direction that reduces the error
6. Repeat millions of times

The problem is memory plus arithmetic intensity, under precisely stated assumptions. A 70-billion-parameter model stored in BF16 uses:

`70 × 10^9 parameters × 2 bytes = 140 GB`

That is **weights only**. Training can additionally require gradients, optimizer state, master weights depending on the precision strategy, activations, temporary buffers, and framework overhead. The total depends on optimizer, activation checkpointing, sharding, batch shape, sequence length, and implementation. Inference memory is different from training memory, and replicated state is different from sharded state. So it is wrong to say that a 70B model is impossible on one GPU under all circumstances; it is correct to say that conventional replicated BF16 training state exceeds a single 80 GB H100 in typical configurations.

<TrainingParallelismViz />

When you split training across many GPUs, those GPUs must communicate constantly. After or during the backward pass, participating ranks combine their gradient contributions -- this operation is called **AllReduce**. AllReduce is a collective **semantic**: every participant in its communication group receives the reduced result. It is not physically implemented by every GPU sending a full tensor to every other GPU. Implementations can use ring, tree, hierarchical, or hardware-assisted algorithms, and communication can overlap backward computation through gradient bucketing.

A four-participant sum example makes the semantic concrete: if GPU 0 contributes 1, GPU 1 contributes 2, GPU 2 contributes 3, and GPU 3 contributes 4, sum-AllReduce returns 10 at all four participants. A ring implementation is commonly explained as reduce-scatter followed by all-gather.

For a conventional ring AllReduce with `N` participants and `S` input bytes per participant, each participant sends:

`2 × (N − 1) / N × S bytes`

and receives the same number of bytes. These are directional byte counts, not sent-plus-received traffic. Examples: `N=4, S=8 GB` gives 12 GB sent per rank; `N=8, S=14 GB` gives 24.5 GB; `N=256, S=14 GB` gives 27.890625 GB.

Collectives operate on defined communication groups. An AllReduce is not necessarily a barrier involving every GPU in the entire training job.

Larger jobs increase synchronization scope and total data movement, but per-rank traffic depends on the collective algorithm. In the ring example above, per-rank sent bytes approach `2S` as N grows rather than scaling without bound. The root network problem is therefore not a simplistic “more GPUs always means proportionally more bytes per GPU”; it is the combination of large messages, synchronized timing, group size, latency sensitivity, congestion behavior, and implementation choices.

This synchronisation pattern creates a distinctive traffic shape called **burstiness**. Between synchronisation points, traffic is moderate -- GPUs are computing, doing forward and backward passes. At a synchronized collective point, participating GPUs can transmit large gradient fragments in the same time window -- traffic spikes sharply, then returns to baseline when synchronisation completes. The fabric must be engineered so congestion-induced loss and excessive queueing do not destroy collective performance. Reliable transports can recover some loss; losslessness is an engineering objective, not a guarantee against every failure.

Buffer depth, ECN threshold placement, and PFC headroom are all sized around this burst pattern.

**Parallelism families and their traffic patterns**

Training is accelerated by splitting the work across GPUs. There are several complementary approaches, and each one produces a different pattern of inter-GPU communication. As a network engineer, understanding which type dominates a given training run tells you what traffic pattern to expect on the fabric.

**Data parallelism** -- All GPUs run the same complete model but on different batches of data. After each training step, participating replicas combine gradients using collectives such as AllReduce. The collective semantic is all-participating-ranks-receive-the-result, but the wire traffic depends on the ring/tree/hierarchical algorithm and group placement. Sharded alternatives such as FSDP and ZeRO change what is replicated and what communication is required. It is not automatically the highest-demand pattern in every workload. A data-parallel collective can create synchronized many-to-many logical communication, even when the physical implementation uses ring or tree forwarding rather than direct pairwise exchanges. Rail-optimized topology and appropriate fabric capacity are designed partly around these demanding collective phases.

**Tensor parallelism** -- A single model layer (for example, a large matrix multiplication) is split across multiple GPUs within a single node. Each GPU handles a shard of the computation and they exchange partial results continuously. Because this communication can be frequent and large, tensor parallelism is often placed inside a high-bandwidth scale-up domain such as the 900 GB/s NVLink domain of the reference node. It can span nodes when the architecture and workload support it, but then external bandwidth and latency become first-order design constraints.

**Pipeline parallelism** -- A model is split by layers. GPU 1 handles layers 1-10, GPU 2 handles layers 11-20, and so on. Data flows sequentially through the pipeline -- GPU 1 sends its output to GPU 2, which processes it and sends its output to GPU 3. The external network traffic is sequential point-to-point rather than all-to-all. Its volume is not universally lower or higher than data-parallel collective traffic; it depends on activation sizes, microbatching, model partitioning, and schedule. Latency and stalls on a stage boundary can still be important because downstream stages depend on upstream output.

**Model parallelism** is an umbrella concept that includes tensor and pipeline partitioning; it is not a fourth independent category. Large-scale training jobs can combine multiple approaches: tensor parallelism within a scale-up domain, data parallelism across nodes, pipeline parallelism across stages, and—when mixture-of-experts models are used—expert parallelism. Exact combinations are model- and implementation-specific. The fabric may need to handle several of these patterns simultaneously. **Expert parallelism**, used in mixture-of-experts models, dispatches tokens to expert shards and combines their outputs, often using All-to-All communication. Traffic volume is architecture- and implementation-specific.

**What this means for the external network**: In the primary reference placement, the external compute fabric carries data-parallel collectives and pipeline stage traffic, while tensor parallelism usually remains inside the scale-up domain. Expert traffic and any cross-node tensor/pipeline placement can also use the external fabric. Congestion during a synchronous collective can delay every participant in that communication group. It is not accurate to assume that every congestion event halts every GPU in the entire job for a fixed duration. A pipeline stall holds the pipeline stage but downstream GPUs can continue processing their current micro-batch.

## Act 3 -- Inside one server first -- NVLink

Before we reach the external network, there is a problem to solve within a single server: how do multiple GPUs talk to each other efficiently?

The answer NVIDIA built is **NVLink** -- a proprietary high-speed interconnect that directly connects GPUs to each other, carrying GPU-to-GPU traffic without using the external PCIe host path for that data. CPU software still orchestrates kernels and communication setup.

<NVLinkViz />

The DGX H100 uses **4th-generation NVLink**, connected through **4 x 3rd-generation NVSwitch chips** inside the chassis. This gives each GPU **900 GB/s** of aggregate bidirectional NVLink endpoint bandwidth. A full-duplex 400G external link has 100 GB/s of aggregate bidirectional capacity, so the consistently normalized nominal ratio is 9:1.

The naming is a common source of confusion: NVLink and NVSwitch use separate generation counters. The H100 has 4th-gen NVLink but 3rd-gen NVSwitch. For reference: the DGX A100 used 3rd-gen NVLink (600 GB/s) with 2nd-gen NVSwitch. The Blackwell B200 uses 5th-gen NVLink (1.8 TB/s). This course focuses on H100 -- 4th-gen NVLink, 3rd-gen NVSwitch, 900 GB/s.

**3rd-generation NVSwitch: more than a crossbar**

The 3rd-generation NVSwitch in the DGX H100 is not just a high-speed crossbar switch. It adds hardware acceleration for collective operations -- specifically multicast and in-network reduction. During an intra-node AllReduce, supported NVSwitch hardware and software can accelerate applicable multicast/reduction operations as data flows through the scale-up fabric, rather than requiring all 8 GPUs to exchange data pairwise. This reduces the work that the intra-node AllReduce requires and lowers the latency of gradient synchronisation within the chassis.

This is the NVSwitch equivalent of what SHARP does on InfiniBand switches -- in-network compute that reduces communication volume by doing part of the mathematical work inside the switch fabric itself. The difference: NVSwitch hardware multicast/reduction applies within the intra-node scale-up domain (the 900 GB/s NVLink domain). IB SHARP applies to inter-node AllReduce (the external fabric). Chapter 0 Act 6 covers IB SHARP. Chapter 12 covers the NVLink Switch System, which extends this capability across nodes.

Bandwidth metrics must not be interchanged. DGX/HGX H100 has eight GPU endpoints at 900 GB/s aggregate bidirectional each, giving 7.2 TB/s of system endpoint bandwidth. NVIDIA separately documents 3.6 TB/s of system bisection bandwidth and 13.6 Tb/s total throughput per third-generation NVSwitch chip. Those are different metrics; do not compare them as if they were interchangeable.

This bandwidth and latency advantage is one reason **tensor parallelism** is commonly placed within a scale-up domain such as one DGX node. It is a common placement decision, not a universal protocol constraint.

NVLink is the scale-up interconnect inside one DGX/HGX chassis in the primary reference example. NVIDIA also sells NVLink Switch System architectures that extend NVLink domains beyond one chassis, and rack-scale GB200 NVL72 systems are different from the eight-GPU DGX B200. When the memory, compute, or scaling requirements exceed what one node can provide, you need an external scale-out network. And that is where the real engineering challenge begins.

## Act 3B -- What AMD does instead: Infinity Fabric and xGMI

NVIDIA uses NVLink and NVSwitch in the reference DGX architecture. AMD Instinct platforms use a different scale-up architecture. The comparison is useful only if the metric and scope are kept consistent.

<AMDvsNVIDIAInterconnectViz />

### The Infinity Fabric stack

**Infinity Fabric** is a family of interconnect technologies. Inside a GPU package, it connects accelerator chiplets and I/O dies. **xGMI** is the external Infinity Fabric link variant used for GPU-to-GPU scale-up connectivity between OAM packages in an eight-GPU platform. Those scale-up links are separate from host PCIe connectivity and separate from external scale-out network adapters.

AMD ROCm comparison documentation uses a metric called **P2P ring aggregate bandwidth**:

| Platform | Memory per GPU | Peak memory bandwidth | P2P ring aggregate bandwidth |
| --- | ---: | ---: | ---: |
| MI300X/MI325X generation | 192 GB HBM3 / 256 GB HBM3E | 5.3 / 6.0 TB/s | 896 GB/s |
| MI350X/MI355X generation | 288 GB HBM3E | 8.0 TB/s | 1,075.2 GB/s |

These are peak aggregate-bidirectional architectural figures. They are not measured RCCL algorithm bandwidth or bus bandwidth. AMD product pages may also report total aggregate I/O or per-link values; those are different scopes and must not be substituted arbitrarily.

<AMDGenerationCompareViz />

The approximately 20% increase from 896 GB/s to 1,075.2 GB/s is arithmetic under one consistently defined metric. It does not prove a universal training-speed ratio. Collective performance depends on message sizes, algorithm selection, clocks, memory pressure, software versions, topology use, and workload partitioning.

### Scale-out networking and UALink

AMD platforms do not require one mandatory AMD NIC model. Platform vendors can select compatible NICs, switches, drivers, and transports. Pollara is one AMD NIC option, not a universal prerequisite. Likewise, NVIDIA and AMD Ethernet deployments are not automatically interchangeable operationally: NIC behavior, congestion control, QoS markings, PFC/ECN settings, telemetry, adaptive-routing support, reordering support, and collective-library tuning can differ.

**RoCEv2 and Ultra Ethernet are not synonyms.** RoCEv2 is the UDP/IP encapsulation of RDMA transport used today. The Ultra Ethernet Consortium is a scale-out networking initiative. **UALink is different again**: it is a scale-up accelerator interconnect specification.

UALink Consortium documentation for the 200G 1.0 specification describes 200 Gb/s per lane. Four lanes therefore provide 800 Gb/s per direction, which is 100 GB/s per direction, with architectures described for up to 1,024 accelerators in a pod. It is incorrect to call this 800 GB/s. Specification availability, shipping hardware, and production adoption are distinct milestones; roadmap statements must be date-stamped rather than treated as existing deployment facts.

### Diagnostic work on AMD nodes

Representative ROCm commands include:

```bash
rocm-smi
rocm-smi --showtopo
rocm-smi --showtopoweight
ibstat
rdma dev show
```

Topology output includes connectivity type, topology weight, and measured or theoretical bandwidth information depending on the tool and version. Do not interpret one weight value as universal proof of a direct xGMI link or a longer path; consult the ROCm documentation for the installed version. ROCm is AMD's GPU software platform, while NIC drivers and RDMA provider software are separate layers. RCCL is AMD's collective communication library, broadly analogous in role to NCCL, but it is not “CUDA plus MLNX-OFED.”

> **Practical summary**: compare like with like. MI325X-class AMD platforms document 896 GB/s P2P ring aggregate bandwidth per GPU; MI350-class platforms document 1,075.2 GB/s. H100 NVLink documents 900 GB/s aggregate bidirectional endpoint bandwidth. These peak scale-up metrics do not by themselves prove tensor-parallel training speed, and they say nothing automatic about which external NIC or Ethernet fabric design must be used.

## Act 4 -- Why conventional Ethernet behavior is not enough

Your first instinct is reasonable: use fast Ethernet. The bandwidth alone is not the problem. The problem is the interaction among congestion, transport recovery, synchronized collectives, and load-balancing behavior.

### TCP loss recovery is more nuanced than “wait for timeout”

TCP can detect loss through acknowledgment behavior, duplicate acknowledgments, selective acknowledgments, modern loss-detection algorithms, and retransmission timeouts. A timeout is not required for every lost packet. TCP retransmission can repair the stream while the connection remains established, though latency and throughput are affected.

### Reliable Connected RDMA loss recovery

Reliable Connected RDMA uses packet sequence numbers. A missing or discontinuous packet sequence can trigger transport recovery. Implementations commonly use Go-Back-N-style retransmission of outstanding data from the missing sequence point, but exact behavior depends on transport implementation and configured retry limits. Two outcomes must be distinguished:

1. **Recoverable loss** -- retransmission succeeds, the transfer completes, and the QP remains operational.
2. **Unrecoverable loss or exhausted retries** -- the work request completes in error and the QP may transition to an error state, forcing the communication library or application to rebuild state.

Outstanding unacknowledged transport data is not the same thing as the full tensor. A single packet loss therefore does **not** automatically put the QP into error state or force retransmission of most of a tensor. A successfully recovered loss can still delay a collective, and collective delay can propagate to every participant in that communication group, but no universal fixed stall duration applies.

<PacketDropCostViz />

AI fabrics are engineered to avoid congestion-induced loss because repeated recovery is expensive in synchronized workloads. That engineering objective is not a promise that physical corruption, transceiver faults, misconfiguration, hardware failure, or software errors cannot occur.

### ECMP entropy, elephant flows, and flowlets

Conventional ECMP normally selects a path per flow by hashing packet-header fields such as source/destination IP addresses, protocol, and source/destination ports. Distinct five-tuples can still collide into the same hash bucket because a large input space is compressed into a small number of paths.

RoCEv2 uses UDP destination port 4791. UDP source ports can provide entropy, but a QP is not guaranteed a globally unique source port, and a multi-rail node can have multiple interfaces and IP addresses. AI training also tends to create a small number of very large elephant flows rather than millions of short mouse flows. When two large distinct flows hash to one member, their combined offered load can exceed link capacity even while other paths remain underused. Carried utilization cannot exceed physical line rate; excess traffic queues or drops.

A **flowlet** is not an indistinguishable flow. It is a burst or segment of packets within a flow, separated from the next burst by a sufficiently large inter-packet gap. A flowlet-aware implementation may choose a different path at a flowlet boundary while controlling reordering risk. Flow hashing, hash entropy, hash collision, elephant flows, flowlets, per-flow routing, flowlet routing, packet spraying, and packet reordering are distinct concepts.

<LowEntropyFlowletsViz />

Uneven utilization is a symptom, not proof. Diagnose offered load, hash placement, queue occupancy, drops, endpoint behavior, and traffic concentration before concluding that ECMP or flowlet behavior is the root cause.

## Act 5 -- What the industry tried, and what won

The journey to today's AI networking infrastructure went through several stages.

<IndustryEvolutionViz />

**2010-2015: Early deep learning clusters**
Researchers used standard Ethernet with TCP/IP. Training was slow but the models were small. The network was not yet the bottleneck.

**2016-2018: The GPU cluster era begins**
Models got larger. Multi-GPU training became necessary. Teams started using InfiniBand -- a technology that already existed in supercomputing -- for GPU-to-GPU communication. InfiniBand was engineered around credit-based congestion-loss avoidance, which matched tightly coupled parallel workloads.

**2019-2020: NVIDIA acquires Mellanox**
NVIDIA announced the approximately $6.9 billion acquisition of Mellanox, a major InfiniBand and high-speed Ethernet adapter/switch vendor, in March 2019 and completed it on April 27, 2020. This was a strategic move: NVIDIA controlled the GPU, and now it controlled the network that connected GPUs. The DGX reference architecture became an integrated product.

**2021-2023: RoCEv2 adoption increases for large AI fabrics**
RoCEv2 existed before this period. RoCEv2 carries RDMA transport messages over UDP/IP/Ethernet. It uses related RDMA concepts but is not the same link/transport protocol as native InfiniBand. For enterprises that already had Ethernet infrastructure, this was attractive. Large RoCE AI fabrics required explicit loss/congestion engineering. This course uses the common PFC/ECN-based design as its reference while treating it as a design choice rather than a universal protocol requirement.

**2024-present: Two camps**
Large AI deployments use multiple fabric families rather than one universal winner:
- **InfiniBand** (Quantum-2 NDR, Quantum-X800 XDR) -- used in some large dedicated AI-training clusters where its fabric features, ecosystem, or operational model fit the design
- **Spectrum-X (RoCEv2 over Ethernet)** -- used in some enterprise, cloud, and multi-tenant designs where Ethernet operations, ecosystem, cost, or integration requirements fit better

Neither is "wrong." The choice depends on workload, budget, and existing infrastructure.

## Act 6 -- Why InfiniBand is still chosen

RoCEv2 and InfiniBand are design alternatives, not universal winners. InfiniBand is often chosen for tightly coupled training clusters for four main reasons.

**1. Congestion-loss avoidance is part of the fabric design**

InfiniBand uses credit-based flow control: under correct operation, a transmitter does not send into unavailable receive buffer space. This is engineered protection against normal congestion-induced buffer overrun. It is not immunity from physical corruption, link failure, hardware faults, discard conditions, misrouting, software errors, or transport retry exhaustion. Saying that InfiniBand “cannot lose packets” is too broad.

RoCEv2 Ethernet designs commonly combine QoS classification, PFC, ECN, congestion control, sufficient buffering, and careful capacity engineering. They can be highly effective, but correctness depends on consistent design and configuration.

**2. SHARP and collective acceleration**

SHARP can perform supported reduction operations in the network for supported InfiniBand configurations, reducing data movement for applicable collectives. Benefit depends on operation type, hierarchy, scale, message sizes, software support, and configuration. It is not a universal fixed percentage improvement, and switch/NVSwitch/software capabilities must be distinguished. NVSwitch reduction/multicast support and InfiniBand SHARP operate in different architectural domains.

**3. Fabric behavior and adaptive routing**

Supported InfiniBand implementations can use adaptive routing and fabric-management mechanisms designed for tightly coupled HPC traffic. Adaptive routing improves path selection but does not make congestion impossible or guarantee perfect balance. A Subnet Manager is required for InfiniBand subnet management; UFM is a broader optional management platform. Recovery time depends on topology, control plane, timers, hardware fast-reroute capability, and failure mode. Do not assume universal microsecond Subnet Manager recovery or universal multi-second Ethernet recovery.

**4. Operational integration**

NVIDIA reference architectures integrate GPUs, adapters, switches, collective software, telemetry, and validation tooling. That integration can reduce deployment uncertainty. It does not mean every InfiniBand fabric is automatically faster or that Ethernet cannot implement sophisticated congestion control, adaptive routing, or collective acceleration.

**PFC and ECN are separate mechanisms**

PFC is priority-specific hop-by-hop pause. It can protect selected traffic classes but requires correct classification, thresholds, and headroom, and it can introduce head-of-line blocking, congestion spreading, or deadlock risk. ECN marks packets to signal congestion; endpoints must respond. Representative RoCE congestion-control implementations use receiver-generated congestion notification packets and sender rate reduction. ECN itself does not prevent loss. Some RoCE implementations can operate without PFC under appropriate transport and network design; this course uses a PFC/ECN-based reference because it is common and operationally concrete, not because it is a universal protocol requirement.

<ECMPViz />

Spectrum-X is NVIDIA's Ethernet architecture combining supported Spectrum switches, BlueField-3 SuperNIC functionality, adaptive packet spraying, receiver-side reordering/direct placement, telemetry-based congestion control, and lossless networking behavior. Do not expand “RSHP” as a product feature unless the exact NVIDIA documentation for the relevant generation does so. Capabilities depend on switch/NIC generation and software. A ConnectX-7 Ethernet deployment does not automatically provide every Spectrum-X capability.

## Act 7 -- The NIC that stopped being a NIC

As networking demands grew, adapter capabilities overlapped and expanded. NIC, RDMA-capable HCA, and DPU are not perfectly separate historical categories; the stages below are a simplified capability progression.

<NICEvolutionViz />

**Stage 1 -- The classic NIC**
Moves Ethernet frames between the wire and host memory using DMA. Modern NICs offload checksums, segmentation, receive-side scaling, interrupt moderation, and other work. Host software still processes TCP/IP and applications; performance depends on the complete system rather than a universal speed at which CPUs “cannot keep up.”

**What RDMA actually does -- the queue model**

To understand why the HCA exists, you need the RDMA resource model. An RDMA device exposes resources to software:

- **Protection Domain (PD)** -- a security/resource boundary.
- **Memory Region (MR)** -- registered memory that the adapter may access.
- **Local key and remote key (lkey/rkey)** -- authorization handles for local access and remote one-sided access.
- **Queue Pair (QP)** -- a Send Queue and Receive Queue associated with a transport endpoint.
- **Completion Queue (CQ)** -- a queue of completed work. A CQ can be shared by multiple QPs; it is not necessarily a dedicated third queue per connection.
- **Work Request (WR)** -- an application-level operation submitted to a queue.
- **Work Queue Element (WQE)** -- the hardware-visible descriptor generated from that request.
- **Work Completion (WC)** -- the completion record later read from a CQ.

Applications register memory, create resources, connect QPs, and post work. The adapter can then DMA registered host memory or supported GPU memory and execute the reliable transport in hardware or firmware. CPU involvement remains necessary for setup, resource management, completion processing, communication-library decisions, error recovery, and application logic. RDMA offload changes what the CPU does; it does not make software disappear.

SEND/RECV operations consume receive buffers posted by the receiving application. RDMA WRITE writes into authorized remote memory and RDMA READ retrieves authorized remote memory; ordinary one-sided operations do not require a matching receive WQE in the same way as SEND. WRITE_WITH_IMM has different receive-completion behavior. Whether an outbound operation produces a completion entry also depends on signaling configuration.

QP count is implementation-dependent. Do not assume one remote GPU means exactly one QP; collective libraries choose channels, connections, and algorithms. The QP number appears in transport headers and diagnostics. Critically, **`ibstat` reports device and port state, not QP state**. QP states such as RESET, INIT, RTR, RTS, and ERR are inspected through Verbs-aware tools such as `rdma resource show qp` or application diagnostics. An active port does not guarantee successful application communication, and a QP error does not imply a physical port failure.

**Stage 2 -- The HCA (Host Channel Adapter)**
An RDMA-capable HCA implements substantial transport processing in adapter hardware/firmware and can DMA registered memory. Host software still creates and manages resources, posts operations, handles completions, and recovers errors. A ConnectX-7 is an RDMA-capable adapter; exact InfiniBand/Ethernet personality depends on SKU, firmware, and configuration.

**Stage 3 -- The DPU (Data Processing Unit)**
The BlueField series goes further. A DPU is a fully programmable SmartNIC with an embedded Arm CPU complex (16 cores in BlueField-3), running a full Linux OS independently of the host. It can offload not just RDMA transport but also:
- OVS offload for eligible virtual-switching functions when configured
- NVMe-oF-related storage services when the platform and software are configured for them
- TLS/IPsec termination for eligible traffic when configured
- Firewall and security policy services

## Checkpointing and the cost of failure

At cluster scale, interruption risk must be engineered rather than treated as a rare exception. Use this as a **simplified illustrative model**, not a measured production failure rate: assume 32,000 GPUs, independent exponentially distributed failures, and a mean time between failures of 10,000 GPU-hours. The aggregate expected interval is:

`10,000 / 32,000 = 0.3125 hours = 18.75 minutes`

Real job interruptions involve correlated failures, CPUs, memory, NICs, links, switches, power, storage, firmware, orchestration, application software, and recovery mechanisms. Do not treat one GPU MTBF as a complete cluster reliability model.

### Checkpoint arithmetic

A 70-billion-parameter BF16 model uses:

`70 × 10^9 × 2 bytes = 140 GB`

That is **weights only**. A full training checkpoint may include optimizer state, gradients, master weights, RNG state, metadata, and framework-specific data, so it can be much larger. Also distinguish total checkpoint size from each node's checkpoint shard.

The ideal transfer duration is:

`duration = size / effective bandwidth`

| Nominal bandwidth | Decimal conversion | Ideal duration for 140 GB |
| ---: | ---: | ---: |
| 100 Gb/s | 12.5 GB/s | 11.2 s |
| 200 Gb/s | 25 GB/s | 5.6 s |
| 400 Gb/s | 50 GB/s | 2.8 s |
| 800 Gb/s | 100 GB/s | 1.4 s |

These are idealized line-rate conversions, not guaranteed storage-write throughput. Achievable time depends on adapter count and configuration, PCIe bandwidth, protocol overhead, filesystem behavior, target throughput, concurrency, checkpoint sharding, synchronization, serialization, metadata, and whether checkpointing is asynchronous. The 3.2 Tb/s compute-fabric aggregate is not automatically available as storage bandwidth.

If a job with `N` GPUs loses `T` seconds of useful work:

`lost GPU-hours = N × T / 3600`

For 32,000 GPUs and a 30-minute checkpoint interval, worst-case lost progress is:

`32,000 × 0.5 = 16,000 GPU-hours`

A uniform failure-time assumption gives approximately half the interval as expected lost progress, but that is an approximation, not a universal production result.

If ideal checkpoint blocking time falls from 11.2 seconds to 1.4 seconds, the saving is 9.8 seconds. If the entire 32,000-GPU job were blocked for that interval:

`32,000 × 9.8 / 3600 = 87.1111 GPU-hours`

<CheckpointCostViz />

The earlier 3.1 GPU-hour figure was wrong. Financial impact requires an explicit cost input. For example, using a purely hypothetical $500/GPU-hour solely as arithmetic, 16,000 GPU-hours is $8,000,000 and 87.1111 GPU-hours is approximately $43,555.56. That rate is not a claimed market price, and no payback period can be inferred without platform cost and operational data.

**Why DGX and not something else?**

There are alternatives. HPE Cray supercomputer nodes, AMD Instinct MI300X servers, Google TPU pods. Each has real strengths. But for the purposes of this course, DGX is the right reference platform because:

- It is widely documented and commonly used as an enterprise AI training reference platform
- NVIDIA's vertical integration (GPU + NIC + switch + software) means the reference architectures are well-documented
- The InfiniBand and RoCEv2 concepts you learn here apply regardless of which hardware you eventually work with

## Why the wiring is rigid by design

Rail-optimized topology is physical wiring plus routing design. In the documented DGX H100 32-node scalable-unit rail design, same-rail endpoints can share the corresponding rail leaf. The full SuperPOD implementation removes one node position for UFM connectivity; that implementation detail does not change the rail-local concept. That does not generalize to every node in an arbitrarily large cluster.

Three cases must be distinguished:

1. **Same rail, same scalable unit** -- the path can remain local to that rail leaf.
2. **Different rail, same scalable unit** -- endpoints use different compute adapters and leaves; the path depends on fabric routing and may use spine/higher tiers.
3. **Same rail, different scalable units** -- spine or higher fabric tiers are needed to cross scalable-unit boundaries.

<RailTopologyViz />

Physical rail wiring and NCCL's logical rings or trees are related but not identical. NCCL chooses communication algorithms and channels using topology discovery, collective type, message size, software version, and configuration. Do not claim that all AllReduce traffic avoids the spine or that all non-rail traffic must traverse it.

### Oversubscription

For a clearly specified topology and traffic direction, oversubscription is:

`total server-facing capacity / available uplink capacity`

Example: `32 × 400 Gb/s downlinks = 12.8 Tb/s`; `16 × 400 Gb/s uplinks = 6.4 Tb/s`; oversubscription is `12.8 / 6.4 = 2:1`.

This constrains traffic crossing the uplinks under sufficient offered load. It does not mean every flow gets exactly half throughput, and it does not mean every training step drops packets. A nominally 1:1 fabric can still congest because of incast, traffic concentration, hash collisions, endpoint limits, or synchronization. Topology capacity and switch buffering are separate resources; undersubscription does not automatically dedicate egress buffer capacity to each leaf port.

### Four functional networks in the reference architecture

NVIDIA's DGX H100 SuperPOD reference architecture distinguishes four functional fabrics. A deployment may physically separate or consolidate them:

1. **Compute fabric** -- GPU collective and inter-node training communication.
2. **Storage fabric** -- dataset access and checkpoint traffic. The NVIDIA H100 reference architecture uses InfiniBand for storage; other deployments can use Ethernet. Do not claim storage is always Ethernet.
3. **In-band management** -- host OS access, provisioning, fabric-management connectivity, telemetry, and operational control using production-network infrastructure.
4. **Out-of-band management** -- BMC/IPMI access through dedicated management infrastructure, intended to remain reachable when production networking fails.

Storage services can include parallel filesystems, shared filesystem services, or NVMe-oF block access. GPUDirect Storage is not synonymous with NVMe-oF. Supported GDS configurations can avoid intermediate CPU-memory staging on the data path, while setup and orchestration still involve host software.

### What mode means

In **InfiniBand mode**, an appropriate adapter uses InfiniBand link and transport behavior. Credit-based flow control protects against normal receiver-buffer overrun under correct operation, but does not make corruption or hardware failure impossible. Native InfiniBand addressing uses LIDs assigned through subnet initialization and the Subnet Manager.

In **Ethernet mode**, the adapter presents Ethernet interfaces. RoCEv2 carries RDMA transport messages inside UDP/IP. Ethernet does not use InfiniBand LID addressing, so LID fields in RoCE output are normally zero. A zero LID alone is not definitive proof of mode in every state: native InfiniBand can also show zero before subnet initialization or assignment.

`mlxconfig` examples are device-specific. `-d` selects one MST device; it does not inspect every NIC merely because the interface represents a rail. Current and next-boot values can differ, and changing link type is an administrative operation that can interrupt connectivity and may require reset or reboot. Do not run it against production infrastructure without a maintenance procedure.

```bash
# Query one explicitly selected device
mlxconfig -d /dev/mst/mt4129_pciconf0 q | grep LINK_TYPE

# Example next-boot configuration on one explicitly selected device
# Administrative/disruptive operation: verify exact SKU, firmware, syntax, and maintenance window first
mlxconfig -d /dev/mst/mt4129_pciconf0 set LINK_TYPE_P1=2
```

OSFP or QSFP form-factor compatibility does not guarantee protocol, lane, signaling, firmware, transceiver, or cable compatibility. The exact same cable is not automatically valid across InfiniBand and Ethernet modes.

### Representative RoCEv2 packet anatomy

RoCEv2 carries RDMA transport messages, not literal serialized Verbs API function calls. A representative reliable-connected RDMA WRITE packet is layered approximately as:

```
Ethernet header
optional VLAN header (PCP is here when VLAN tagging is used)
IPv4 or IPv6 header (including DSCP and ECN bits)
UDP header (destination port 4791; source port can provide flow entropy)
Base Transport Header (opcode, P_Key, destination QPN, AckReq, 24-bit PSN)
operation-specific extended transport header (for WRITE, RETH carries remote address/rkey/length)
payload where applicable
invariant CRC
Ethernet FCS
```

Different opcodes have different extended headers and payload layouts. Acknowledgments use an AETH extended transport header; AETH is not generic application payload. The PSN is finite width and wraps rather than increasing forever. UDP source-port entropy can help ECMP, but a QP is not guaranteed a globally unique source port.

### Classification is configuration, not protocol magic

A UDP destination port of 4791 does not automatically place traffic in a PFC-protected priority. DSCP 26 is a commonly used reference marking, not a requirement of RoCEv2. VLAN PCP and IP DSCP are different header fields. The illustrative chain is:

`packet marking -> switch trust/classification -> internal traffic class/priority mapping -> queue and PFC/ECN policy`

Switch platforms implement this differently. A break in trust, mapping, queueing, PFC, or ECN configuration can defeat the intended lossless design. Chapter 5 validates that operational chain in detail.

### Infrastructure consequences

<IBvsRoCEInfraViz />

Native InfiniBand adapters connect to InfiniBand fabrics. RoCEv2 adapters connect to Ethernet fabrics. Switch families, operating systems, management tools, telemetry, congestion controls, and diagnostic commands differ. A Subnet Manager is required for an InfiniBand subnet; UFM is a broader management platform rather than a synonym for the SM. Use exact model and software documentation for operational commands; this chapter intentionally stays architectural.

The DGX node GPUs, NVLink domain, CPUs, memory, and local storage do not change personality with the external adapter mode, but host networking configuration, drivers, fabric management, QoS, troubleshooting, cabling validation, and switch architecture do. The storage fabric is not universally Ethernet or universally separate in every deployment; use the selected reference architecture.

Neither fabric choice is universally better. InfiniBand can fit tightly coupled dedicated training clusters that benefit from its ecosystem and fabric features. RoCEv2 can fit organizations prioritizing Ethernet operations, interoperability, tenancy, cost, or existing expertise. Claims such as a universal 5-10% performance gap are unsupported without a specified benchmark, workload, topology, hardware, measurement metric, software versions, and configuration.
