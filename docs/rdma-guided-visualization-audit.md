# RDMA guided visualization audit

Implementation review for the corrected unified guided-navigation curriculum. The audit uses canonical Foundations V2 and Operations V2 text as content authority; it does not treat a rendered component as sufficient evidence of teaching quality.

## Correction audit method

Each guided transition is classified by the technical difference it is intended to establish: orientation baseline, resource/memory/instruction state change, newly revealed evidence artifact or observation, introduction of a new mechanism/failure case, or comparison/interpretation. A presentation-only title change is not accepted as a meaningful difference. Stage explanations are deterministic selections from stable canonical content blocks; every guided stage uses explicit semantic references rather than proportional sentence-window selection. The complete authored subsection remains available in a secondary disclosure, but the learner is not required to open it for the current stage explanation.

## Corrected high-risk sequences

| Mechanism | Current guided sequence and acceptance result |
|---|---|
| Hardware/software responsibilities | Four stages remain. Physical components are introduced first, then a logical software overlay, then application execution and kernel execution inside the same architecture. The CPU-memory relationship is bidirectional and the application/kernel cards are software overlays rather than processors. |
| Process creation | Storage → process A → independent process C → shared read-only mapping → unpopulated demand mappings → A-only touch/population. Future shared and demand rows are absent before introduction. |
| Virtual address translation | Only the active instruction is displayed. A load is translated in A, the byte is returned, the same numerical VA is then resolved in C, a permitted store mutates the illustrated byte, and a read-only store is rejected without mutating memory. |
| Buffer allocation | No buffer → `bytearray(16)` creates sixteen zero cells → HELLO write → capacity/payload comparison. Artificial separate “display already allocated cells” state removed. |
| Copy versus reference | Reference beta mutation changes the original continuously to XELLO; the independent copy is created from XELLO and then independently modified. No silent reset to HELLO occurs. |
| TCP segmentation | Primary view is the aligned application-send, captured-segment and application-read rows with compact selected-frame facts. Full packet table/checksums/raw bytes remain optional. The final comparison selects no single frame. |
| TCP acknowledgement wording | Corrected: acknowledgements identify next expected sequence number; SYN/FIN each consume one sequence position; an ACK flag alone does not. |
| Work Request construction | Operation/WR ID → local memory description linked to registered memory → actual separate SEND source excerpt. The illustrative WR remains unposted. |
| Packet encapsulation | Captured packet orientation → Ethernet/IPv4 → UDP/4791 → BTH/application-data portion → conclusion. Detailed QPN/opcode/length analysis remains in later subsections. |
| Packet lengths | Compact categories plus complete six-form comparison: SEND request/ACK, WRITE request/ACK, READ request/response. ACK/READ-response structures include AETH with the export decoding limitation stated. |
| Code-to-wire correlation | Grouped remote-memory values, endpoint/sequencing context and local-only values, followed by the complete Python → WR → packets → completion/control/verified-memory chain. |
